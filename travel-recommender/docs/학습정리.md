## 1. REST API의 요청/응답 구조와 GET/POST의 차이

REST API 요청은 **메서드 + URL + 헤더 + (요청 본문)** 네 부분으로 구성되고, 응답은 **상태 코드 + 헤더 + 본문(주로 JSON)** 으로 돌아온다. 이 프로젝트에서 Kakao 장소 검색은 `requests.get(url, headers=..., params=...)` 처럼 **GET + 쿼리스트링**을 쓰는데, "데이터를 조회만 하고 서버 상태를 바꾸지 않는" 안전한(safe) 동작이라 검색 조건을 URL에 실어 보내는 것이 자연스럽기 때문이다. 반대로 Gemini 호출은 `requests.post(url, headers=..., json=payload)` 처럼 **POST + 요청 본문**을 쓴다. 프롬프트·모델 설정·온도 같은 길고 구조화된 데이터를 보내야 하는데, URL은 길이 제한이 있고 서버 접근 로그에 그대로 남기 때문이다. 인증 정보는 두 경우 모두 URL이 아니라 **헤더**에 담았고(`Authorization: KakaoAK ...`, `x-goog-api-key: ...`), 응답은 상태 코드로 성공 여부를 먼저 판정한 뒤 `200`일 때만 `response.json()`으로 본문을 해석했다.

**실제로 겪은 것**: 상태 코드는 제공자마다 의미가 미묘하게 다르다. Gemini는 API 키가 틀려도 `401`이 아니라 **`400`(`API_KEY_INVALID`)** 을 보내서, 상태 코드만으로는 "요청을 잘못 만든 것"과 "키가 틀린 것"을 구분할 수 없었다. 그래서 `classify_llm_http_status()`에서 상태 코드와 응답 본문을 함께 보고 판단하도록 만들었다.

```python
# place_client.py — GET: 조회이므로 조건을 URL 쿼리스트링(params)에 싣는다
response = requests.get(KAKAO_KEYWORD_SEARCH_URL, headers=headers,
                        params={"query": "제주 맛집", "size": 5}, timeout=20)

# llm_client.py — POST: 길고 구조화된 데이터를 요청 본문(json)에 싣는다
response = requests.post(endpoint, headers=headers, json=payload, timeout=20)
```

## 2. LLM 출력을 JSON으로 구조화해 다음 단계 입력으로 넘기는 흐름과 그 장점

이 프로그램의 1단계는 LLM에게 "설명 없이 4개 키만 담긴 순수 JSON"을 요구하고, 그 결과의 `recommended_city` 값을 그대로 2단계 검색어 `f"{city} 맛집"`으로 넘긴다. 만약 자연어 문장으로 받았다면 "광양이 좋겠네요!" 같은 답에서 지역명을 정규식으로 긁어내야 하고, 모델이 표현을 조금만 바꿔도 코드가 깨진다. JSON으로 받으면 **키 이름 자체가 계약(contract)** 이 되어 다음 단계가 "문장 해석"이 아니라 "데이터 접근"으로 바뀌고, 파일 저장(`_raw.json`)·재실행·테스트에도 그대로 재사용할 수 있다.

다만 LLM은 형식을 어길 수 있으므로 `json.loads`가 성공했다고 안심하면 안 된다. 이 프로젝트는 파싱 후 **키 존재 여부와 타입까지 검증**(`validate_recommendation`)하고, 실패하면 더 강한 제약 프롬프트로 **딱 1회만** 재시도한 뒤 그래도 안 되면 기본값(fallback)으로 진행한다. 즉 **"구조화 요청 → 파싱 → 스키마 검증 → 제한된 재시도 → fallback"** 이 한 세트로 묶여야 실전에서 버틴다.

**실제로 겪은 것**: Gemini의 구조화 출력 기능(`responseMimeType: "application/json"`)을 켜 두어도 안심할 수 없었다. 최신 모델은 답하기 전에 속으로 추론하는 **"생각(thinking) 토큰"** 을 쓰는데 이것도 `maxOutputTokens` 예산을 함께 소비한다. 한도가 부족해 JSON이 중간에 끊기면서 `Unterminated string` 파싱 오류가 났고, 토큰 한도를 올려 해결했다. **API가 형식을 보장해 줘도 코드 쪽 검증과 fallback은 여전히 필요하다.**

## 3. 외부 API 호출의 대표 오류와 각각의 대응 원칙

**인증 오류(401/403)** 는 키가 없거나 틀렸거나 권한이 없는 경우다. 재시도해도 절대 해결되지 않으므로 즉시 기록하고 "키 설정을 확인하라"고 안내하는 것이 정답이다. **쿼터 오류(429)** 는 호출 한도 초과라 시간이 지나야 풀린다. 즉시 재시도하면 상황을 악화시키므로 **재시도 대상에서 일부러 제외**했다. **네트워크 오류/타임아웃**은 일시적일 수 있어 재시도가 유효하지만, `timeout`을 반드시 지정해야 응답 없는 서버 때문에 프로그램이 영원히 멈추는 사태를 막을 수 있다. **파싱 오류**는 서버는 정상 응답했지만 내용이 기대와 다른 경우로, 전처리(코드블록 제거)와 제한된 재시도로 흡수하고 최종적으로는 기본값으로 진행한다.

네 가지에 공통으로 적용한 원칙은 **"조용히 삼키지 않는다"** 이다. 모든 실패는 `add_error()`로 `{step, type, message}` 형태로 남기고 콘솔에도 즉시 출력하며, 그럼에도 **다음 단계는 계속 진행**해 사용자가 최소한의 결과물은 손에 쥐게 한다.

**실제로 겪은 오류 5종** (모두 프로그램이 죽지 않고 기록 후 완주했다):

| 상황 | 응답 | 대응 |
| --- | --- | --- |
| 기본 모델이 단종됨 | `404 no longer available` | 버전 고정 이름 대신 항상 최신을 가리키는 별칭(`gemini-flash-latest`) 사용 |
| 서버 일시 과부하 | `503 high demand` | **2초 → 4초 백오프로 최대 2회 재시도** (고쳐질 오류이므로) |
| 무료 한도 소진 | `429 exceeded quota` | **재시도하지 않음** (다시 불러도 악화될 뿐) |
| 폐기된 키 사용 | `401 already deactivated` | 재시도 무의미. 즉시 기록 후 키 재발급 안내 |
| 서비스 미활성화 | `403 disabled OPEN_MAP_AND_LOCAL` | 인증은 통과했으나 앱 설정 문제. 메시지를 그대로 남겨 원인 추적 |

**"재시도는 고쳐질 오류에만 한다"** — 이것이 이번에 가장 크게 배운 원칙이다.

## 4. API 키를 코드에 직접 쓰지 않고 .env/환경변수로 관리하는 이유

가장 큰 이유는 **git 히스토리는 지워지지 않는다**는 점이다. 코드에 키를 적고 커밋하면 나중에 지워도 과거 커밋에 값이 남고, 공개 저장소라면 자동 스캔 봇이 몇 분 안에 찾아내 도용한다. 그래서 유출 시 유일한 정답은 "즉시 재발급"이다. 둘째, **환경마다 다른 값을 코드 수정 없이 쓸 수 있다** — 팀원마다 각자의 `.env`만 갖고 같은 코드를 실행할 수 있다. 셋째, **"코드는 공유 대상, 설정은 비공유 대상"** 이라는 경계가 명확해지고, `.env.example`로 "무슨 키가 필요한지"만 안전하게 공유할 수 있다.

이 프로젝트는 여기에 더해 세 겹의 안전장치를 뒀다. ① 시작 시 키 존재를 먼저 검사해 없으면 안내 후 종료(fail fast), ② 로그에는 `mask_api_key()`로 **앞 4자리만** 노출, ③ `register_secret()` / `scrub_secrets()` 로 **API 응답 본문에 키가 섞여 돌아오는 경우까지** 자동 마스킹.

**실제로 겪은 것**: ③번이 실전에서 작동하는 것을 확인했다. 폐기된 키로 호출하자 카카오 서버가 **오류 메시지 안에 키 값을 그대로 담아** 돌려보냈는데, 프로그램이 이를 자동으로 가려서 기록했다.

```
"message": "HTTP 401: {\"errorType\":\"AccessDeniedError\",
            \"message\":\"appKey(05be*****************) is already deactivated\"}"
```

키를 직접 출력하지 않도록 조심하는 것만으로는 부족하다. **외부에서 흘러 들어오는 데이터에도 키가 섞일 수 있다**는 것을 전제로 방어해야 한다는 점을 배웠다.
